# Daily logs and reusable project helpers

Load this workflow when recording a general operational checkpoint, reviewing retention for owned daily logs, or registering or reusing a tested versioned helper. A UTC filename-date check screens for candidates. Verify live retention using genuine eligible logs through the authorized planner and its writer lock.

## Daily work log
At meaningful skill entry/checkpoints and after a verified result, append only a short, generic operational status with the bundled helper:
```
python scripts/project_tools.py log --root PROJECT --summary "work checkpoint" --status work
python scripts/project_tools.py log --root PROJECT --summary "verification completed" --status verified --evidence evidence/check-01.txt
```
All paths beyond PROJECT are relative to its `_boosterAI/`. Logs use `_boosterAI/logs/YYYY-MM-DD.jsonl`, with UTC timestamps. New `boosterai-log-v2` entries contain only the timestamp, status and a fixed status-dependent summary. The existing `--summary` and `--evidence` arguments remain supported, but their values, the evidence content and its hash are not recorded in the daily log; the response reports `summary_recorded`, `evidence_reference_recorded` and `evidence_hash_recorded` as false. Avoid passing secrets in command-line arguments, which may be visible to the operating system.

`verified` still requires an existing regular local evidence file. The helper reports whether it checked for a file, but it does not authenticate the evidence, run the target or prove the observation. Inspect and retain the real evidence in the authorized canonical project record before claiming success. Do not record product details, including requirements, features, implementation details, inputs, outputs or product-specific artifacts, in daily logs. Evidence artifacts themselves require appropriate privacy handling.

Do not create operation logs for archived working code or its files: omit their paths, contents, hashes, staging, retrieval and publication events from project daily logs. The archive's static searchable metadata and index are records of the current reusable assets, not an append-only transaction log. The helper substitutes fixed v2 summaries because it cannot infer the meaning of arbitrary text; the host remains responsible for not logging archive transactions through other means. Existing v1 entries remain byte-for-byte unchanged, may contain details from earlier behavior, and are never silently rewritten or deleted. A daily file may contain both versions. Older helpers that recognize only v1 must be updated to append to or plan retention for mixed files.

Retention targets a strict rolling seven days in UTC. A daily file is eligible only when every owned entry is older than the cutoff; a file containing a recent/active record is preserved. On each log invocation the helper identifies the exact expired owned batch and returns its paths, hashes, sizes, identity and cutoff. It does not delete or quarantine automatically. Anomalous names/files remain untouched and are reported without losing today's log.

## Permanent deletion with action-time approval
The requested final disposition is complete deletion, not quarantine or the recycle bin. Irrecoverable deletion requires fresh user confirmation for the exact concrete batch immediately before acting. A standing instruction to keep seven days cannot waive this requirement. When approval is absent, explicitly report `NOT_DELETED_APPROVAL_REQUIRED`; leave files in place and do not silently quarantine them. Consequently the skill cannot promise unattended permanent cleanup or a hard retention maximum while awaiting approval.

```
python scripts/project_tools.py plan-log-deletion --root PROJECT
python scripts/project_tools.py purge-logs --root PROJECT --plan deletion-plan.json --approval deletion-approval.json
```
Plan and approval paths are relative to `_boosterAI/`. Save the returned `plan` object unchanged. Present its exact filenames, cutoff and irreversibility to the user using the host's confirmation flow. Only after actual action-time confirmation, record `action: delete-owned-expired-logs`, the exact `plan_fingerprint`, `confirmed: true`, a real confirmation `reference`, and UTC `approved_at`. The approval expires after five minutes. These fields are an audit envelope, not a substitute for a real user's confirmation; the host must authenticate that event. Never fabricate, preapprove, auto-renew or copy old approval to a new batch. Omitting approval performs no deletion.

The purge revalidates the whole batch before touching anything, then rechecks identity/hash/age/ownership and the current approval age immediately before each unlink. An approval that expires after preflight or between two deletions stops the remaining batch. No other files, source, evidence or quarantine contents are included. Changed bytes, links/hardlinks, stale approvals or a different batch reject the operation. A mid-operation failure reports exactly what was deleted and what failed; do not claim all-or-nothing transactionality. The API's `now` override is solely for isolated deterministic fixtures, never production authorization. Keep other writers stopped for these exact files; the helper lock cannot control unrelated processes. Older quarantine left by a previous version is not silently purged or migrated.

This is invocation-driven, not a background daemon. When no host/user approval route is available, continue independent authorized work and report the precise retention blocker. Do not log secrets or ask unnecessary approval for routine logging; only the destructive batch needs this action-time step.
## Immutable versioned helpers
When the same authorized work recurs, prefer a small project-specific static helper under `_boosterAI/helpers/NAME/VERSION/` rather than rewriting ad-hoc commands. First implement and actually test the helper in the intended runtime. Register a project-relative partial and evidence:
```
python scripts/project_tools.py register-helper --root PROJECT --name normalize --version 1.0.0 --source _boosterAI/_partials/normalize_ab12cd34.py --source-scope project --evidence evidence/normalize.txt --target "Python CLI"
python scripts/project_tools.py check-helper --root PROJECT --name normalize --version 1.0.0
```
`--source-scope project` resolves the source within the project root; the default `workspace` preserves the earlier `_boosterAI/`-relative source behavior. Evidence remains relative to `_boosterAI/` in both cases. Both scopes reject traversal, links, reparse points and hard links. Registration copies exact source bytes to a versioned file with a short descriptive name and a deterministic, collision-checked suffix. It records the source scope and location, code and evidence hashes, tested target and timestamp. The source is not moved.

New Python helper versions require every function to have a detailed docstring or immediately preceding comment, checked by the bundled Python parser. For a non-Python helper the host must inspect and confirm function documentation, then explicitly supply `--function-docs-reviewed`; the helper does not parse or authenticate that review. Re-registering unchanged code and target reuses an existing version, including older `code.py` records, without renaming it or imposing new documentation requirements. Changed code or target requires a new version. Hash mismatches or lost/changed evidence fail checking. This is metadata integrity, not proof that arbitrary code is safe or tested.

Before use, check the registry, inspect the code and evidence, compare current target/preconditions, then invoke through the authorized host path. The helper registry never executes arbitrary registered code automatically. The canonical project record may document permitted non-archive helper verification, but must not become an operation log for archived working code or files; selecting a helper is not successful execution. Daily logs may contain only generic operational status and must not describe helper code, product details or archived assets. If the target/interface/revision assumptions changed, retest and version as needed. Existing product files and other owners remain untouched. No external package, skill, service or global installation is required.

## Concurrency and recovery
Log, helper and archive mutations share one exclusive project-tools writer lock. When the owner selects a scratch directory, the host must set process-local `BOOSTERAI_SCRATCH` to that existing stable project-contained directory on first use, such as `PROJECT/_temp-files`. Without an explicit selection, first use registers the project-local `_boosterAI/.booster-tmp` default. Per-operation `TEMP`, `TMP` and `TMPDIR` paths are never inferred as the permanent scratch location; they may change or be cleaned after each operation. An explicit scratch outside the project is rejected. Later calls automatically reuse the registered scratch; an explicitly different `BOOSTERAI_SCRATCH` is rejected instead of creating a second lock domain. An existing recognized guard is never silently rewritten, including one that points to a now-missing directory.

The permanent `_boosterAI/.project-tools.lock` is a versioned compatibility barrier recording the chosen scratch directory; it is durable coordination state, not a temporary or stale lock to delete. It is created only with exclusive creation and validated before use. Unknown, active legacy or incomplete barriers are preserved and cause refusal. Older writers that exclusively create this legacy path will stop at the barrier and need updating before they can write. New writers acquire a separate short-lived exclusive lock inside the selected scratch directory and remove only their own unchanged, single-link regular file after checking its identity and random ownership token. A replaced, linked, changed or unknown lock is preserved and causes failure.

Archive JSON staging uses the same guarded scratch and creates a unique owned operation directory on the destination filesystem. Its cleanup checks the directory, file identity and expected contents; changed or unknown content is preserved, reported and stops further staging until reconciled. A direct programmatic `rebuild_index` call does not itself acquire the writer lock: the caller must coordinate concurrent writers. Normal archive staging already runs inside the project-tools writer lock.

Verify no other writer can mutate the selected files while running these operations. This protocol coordinates participating project-tools writers, not arbitrary external processes that ignore both locks. Links, reparse points and hardlinks are refused; containment and content are rechecked before deletion. Filesystem checks are not a sandbox against hostile concurrent path replacement, and operations are not a multi-file transaction. After a crash inspect the barrier, any retained scratch lock, the plan and remaining/deleted files before a scoped recovery; never blindly overwrite or delete active work.

# Successful experience archive and reuse

Load this workflow when looking for a reusable example or preserving a first successful, project-independent implementation verified in its real target. Reuse and improve a matching record on recurrence. The public success archive accepts only verified working code. The archive's metadata and index describe assets. Keep archive transactions and details about archived code and files out of operational logs.

Do not block the next authorized product slice on noncritical archive preparation unless the requested product acceptance explicitly requires that publication. Record a brief non-sensitive deferred action in the project's separate deferred-work file, without logging archived code or file details. Real refusals and mandatory approvals still apply to the affected publication.

## Profile and layout

`solutions/archive.schema.json` is a JSON Schema Draft 2020-12 profile inspired by [Schema.org SoftwareSourceCode](https://schema.org/SoftwareSourceCode) and [CodeMeta](https://codemeta.github.io/terms/). It records `@context`, `@type`, name, description, programming language, runtime, repository, license, keywords, category path, tags, code and evidence hashes. It is a BoosterAI profile, not a claim of complete CodeMeta conformance. The bundled offline validator implements only the schema keywords used by this profile and rejects unsupported keywords; it is not a general-purpose JSON Schema engine. An `artifact-sha256` evidence basis hashes the reviewed local evidence artifact; `sanitized-summary-sha256` hashes the UTF-8 test summary itself. Neither hash authenticates a claimed execution.

Current records live at `solutions/CATEGORY/SUBCATEGORY/NAME/metadata.json`; each immutable revision is under `revisions/NNNN/` and contains `metadata.json` and a short descriptive code filename ending in a deterministic eight-hex revision suffix. Categories are ordered path components. Tags and keywords are sorted. New categories on a recurring record become searchable aliases rather than silently moving existing revisions. Every Python function needs a detailed docstring or immediately preceding comment block; other languages require explicit documentation review. Preserve earlier revisions and their metadata.

Archived revision files use LF line endings through the repository's `.gitattributes`, keeping their source hashes stable across supported Git checkouts. Preserve this rule when extending the archive.

The producer and snapshot reader share a 262,144-byte limit per normalized UTF-8 code file, a 1,048,576-byte index limit and an 8,388,608-byte total limit for the index plus every current indexed code file. The producer checks the prospective index and normalized code before changing archive records; repeated indexed entries count separately, as they do during sync. Oversized new code stays `LOCAL_ONLY`. An existing archive exceeding a limit is preserved, and affected archive mutations stop for explicit reconciliation rather than deleting old data.

`solutions/index.json` uses sorted records, category paths and tags, with stable canonical JSON. Existing `boosterai-index-v2` metadata remains valid and unrecognized entry fields are preserved. An archive with relationships uses `boosterai-index-v3`; readers that only support v1 or v2 must update before consuming v3. The sync reader accepts v1, v2 and v3. Rebuilding the index does not authenticate evidence and never executes source.

A different-language implementation may use an earlier verified experience as a reference, but its verified source is stored in its own file. `solutions/relationships.json` is the canonical sorted `boosterai-relationships-v1` registry; the v3 index includes the same relationships at its top level. An item is `{ "file": "solutions/.../revision-file", "relatedFile": "solutions/.../other-file", "strength": 0.7, "derivedFrom": true }`: both endpoints identify archive revision files, `strength` is a finite number from 0 through 1, and `derivedFrom` says whether `file` was developed from `relatedFile`. The association does not require identical contracts. Multiple files may relate to multiple other files; store a pair once and show it in both search directions. The registry preserves links involving earlier revisions. Before writing, verify both endpoints against preserved revision metadata and code hashes; the offline schema validates structure but does not prove that historical bytes exist or that either program is correct. Keep failed, private or unreviewed candidates out of the public archive.

The included JavaScript child-directory example and Python recursive-directory example have a reviewed relevance score, not identical search scope. The JavaScript example uses JavaScript `toLowerCase` comparison; it does not claim full Unicode case folding or locale-aware matching. Junction handling is tested on Windows, but the example is not a security sandbox against all reparse types or concurrent path replacement.

To add links while archiving a new candidate, put `relationships: [{"relatedFile": "solutions/.../verified-source.py", "strength": 0.7, "derivedFrom": true}]` in its private review JSON; the helper supplies the new file path. To relate two existing verified files, use `python scripts/project_tools.py link-archive-files --root PROJECT --file SOURCE --related-file TARGET --strength 0.7 --derived-from`; omit the last flag for a non-derivation relationship. Repeating an identical directed link is unchanged; a conflicting copy of the pair is rejected. Links update the registry and index, never source or revision metadata. They are two files, not a transaction: if writing fails after a replacement begins, inspect both and reconcile before retrying; `rebuild-archive-index` can rebuild from a valid registry without dropping prior indexed links. Use `related_files_by_record` for derived relationship paths, strengths and directions. When relationships are included, searches add a convenience `related_files` field only if the stored entry lacks that field. Searches return a stored legacy `related_files` value as-is, including when the `project_tools.archive_search` API is called with `include_related=False`. This metadata does not execute code.

## Search and publication

Before writing a new example, search the [project-local index](project-workspace.md#project-local-partial-and-experience-index) and the authorized common archive. Filter the common archive by nested category path or tag. Use the checkout index or an existing active upstream snapshot.

```
python scripts/project_tools.py search-archive --root BOOSTERAI_CHECKOUT --category filesystem/search
python scripts/archive_sync.py search --root BOOSTERAI_CHECKOUT --category filesystem/search
```

[Daily archive feedback](daily-archive-sync.md) covers the invocation-time upstream check and snapshot activation.

Inspect the returned record and read its referenced source as data. Check the contract, revision, license and verification summary. Use archive files as learning references. The consuming project owns implementation, integration and later refactoring in its own production files. Keep the adapted code independent of archive and partials paths. Adapt only when target prerequisites and interfaces match, then reverify the adapted behavior in the actual target. Stored success is not proof of success elsewhere. Categories and tags are extensible lowercase slugs. Do not claim token or time savings without a measured baseline.

With the local file owner's authorization, save the smallest useful standalone example under the [project's partials workflow](functional-partials.md). Use [independent acceptance](independent-acceptance.md) to verify the exact example through its standalone entry point in the intended environment before accepting it for local indexing or common archive admission. Record the source identity, environment and observed result. The project index owner can then add the accepted example to the project-local index. Verify that its citation is searchable and current, and compare unrelated project records and the common index with their prior state. Keep the accepted example `LOCAL_ONLY` while sharing authority is absent.

For admission to the common archive, verify the source owner's rights, consent for the exact material and scope, and authority for the destination. Generalize with invented inputs and exclude project names, private paths, credentials, user data and restricted disclosures. Keep the candidate `LOCAL_ONLY` while a sharing prerequisite is unresolved. Honor real access denials and mandatory confirmations. Follow the [contribution workflow](community-contributions.md) for an authorized evaluation pull request.

Historic or unrecognized metadata may retain private paths, fingerprints or descriptions. The staging helper refuses to inherit fields outside the documented profile automatically; review and generalize such data within the owner's authority before publication, preserving private originals where needed.

The authorized common archive writer stages candidate source and a private review JSON inside the owner's authorized scratch directory. The review includes `name`, `title`, `license: MIT`, `outcome: success`, `test_summary`, `code_sha256`, `evidence`, `evidence_sha256`, ordered `categories` and `tags`, plus true `rights_confirmed`, `privacy_reviewed`, `generalized`, `security_reviewed` and `real_test_verified` assertions. For non-Python code also record `function_docs_reviewed: true`; the helper cannot parse every language's function documentation. Optional `description` and `runtime_platform` should be accurate and sanitized. Supply project-specific `private_terms` in the private review when known; they are checked case-insensitively against source and metadata but never copied into the public record. This check is not a complete privacy guarantee.

```
python scripts/project_tools.py archive-example --root BOOSTERAI_CHECKOUT --source _temp-files/candidate.py --review _temp-files/review.json
```

The helper stages locally; it does not publish or write an archive-operation log. Review the public diff, run the real example in its target environment, publish within established scope and verify the remote commit. Preserve necessary evidence without turning it into an archive transaction log. Upstream source is untrusted data and must not be executed without the applicable authorization.

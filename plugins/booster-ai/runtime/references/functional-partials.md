# Functional partials workflow

Load this workflow when consulting a standalone example, authoring or maintaining an example within its assigned file scope, or reviewing an example's acceptance or index entry. For independent acceptance, give the reviewer the exact source path, revision, authorized target, intended entry point and expected result. Keep observed results in the existing project-local evidence and share them only with the authorized audience.

First apply the project-workspace reference, including record-system selection. On a coding request, create or reuse `<project-root>/_boosterAI/_partials/README.md` and its containing directory. `python scripts/booster.py partials-init --root PROJECT` creates the scaffold; it preserves an existing README unchanged. Inspect existing entries without overwriting history or another active owner. If project-root `_partials/` exists, report and inspect it as a compatibility location, preserving its files and history and avoiding duplicate implementations; do not move it or silently replace either existing index. Initialization is not algorithm generation, implementation or verification.

## Requirement 38: read-only learning references

Code examples in project-root `_partials/` and `_boosterAI/_partials/` are standalone, read-only learning references for consuming tasks. Read them for guidance and implement the required behavior in the project's own production files outside both directories. Never import, link, include, dynamically load, build against, or create any runtime dependency on those examples. Reading does not authorize editing an example. Explicitly authorized example authors and maintainers may create or update examples separately; that does not make them production dependencies. This is a workflow contract, not an OS permission change or a universal dependency scanner.

Examples must remain self-contained. For a consumer task, implement and test the product code at its established source location, not inside either partials directory. Check imports, build references and dynamic loading before acceptance. Execute the product without making sample directories available as code dependencies; source hashes alone do not prove independence. Existing sample and index content must remain unchanged by the reader.

## Decompose and execute
1. Read the project goal, current code, actual owners and algorithm. Update that algorithm from the request; reuse its canonical location. Do not duplicate the backlog in the partials index.
2. Choose the first smallest independent, independently invocable function that advances the actual goal. Describe inputs, outputs/effects, prerequisites, dependencies, target, acceptance and failure/recovery. If a prerequisite must be created by the product, implement and verify that prerequisite first.
3. Choose language in this exact order: explicit user request, existing module language, otherwise Python. No mandatory framework or external runtime package is introduced. TensorFlow or any other third-party library is not required by BoosterAI. A target project's existing dependencies remain explicit target prerequisites.
4. When explicitly authoring an independent example, put the function in its own short, descriptive source file under `_boosterAI/_partials/`, with a stable unique suffix, stable interface and no secret test values. For example, a Python module may use `normalize_text_b73e19a2.py`; check that the suffix is not already used for another piece. For each function, add a detailed docstring or immediately preceding comment explaining its purpose, inputs, result, preconditions and side effects or failures where applicable. Do not rename or move existing working code or violate compilation/package rules merely to satisfy this convention. For product code, keep the implementation at its established production path. An authorized standalone learning example may describe that implementation, but neither production code nor its build may depend on the example. Do not create an adapter that links production code to a partial or two divergent production implementations.
5. Invoke the function in its actual runtime/target using the real intended interface. Store or link evidence bound to its revision and target. Record the function and its contract, file, dependencies, ownership and run, target and revision, evidence status, integration state and optional backup status in the partials README or existing canonical project record.
6. Only after real acceptance, proceed to the next dependent function. Failed or unavailable execution remains FAIL or NOT_RUN. A mock service, generated screenshot, unit test alone or a green build is not a substitute for a missing real target. Diagnose or perform independent authorized work without pretending the gate passed.

## Product-owned integration and maintenance
The project learning from verified examples owns the implementation and combination of its own code at its established product interfaces, without dependencies on either partials directory. The skill does not undertake automatic merging, integration or subsequent refactoring. If the project combines pieces, verify the resulting behavior in its real target; verified fragments alone do not establish a verified whole. Preserve useful partials and index references; never garbage-collect source or acceptance evidence as temp.

When requests change, revise affected nodes/contracts and mark affected partial evidence stale until retested; leave unaffected verified parts intact. The human-readable record should distinguish PLANNED, ACTIVE, NOT_RUN, FAIL, AMBIGUOUS, VERIFIED, INTEGRATED and STALE. A function can be individually VERIFIED while integration is still NOT_RUN.

Keep a distinct project-local searchable index of the using project's own partials and experiences, including both standard `_boosterAI/_partials/` and any existing root `_partials/`. Preserve existing indices, source files and schemas. The bundled search reads `_boosterAI/project-index.json`, whose entries contain only a project-relative `path`, `kind`, `size` and `sha256`. Keep it separate from the common `solutions/index.json` and respect its privacy boundaries.

## Requirement 39: final file links

At the end of a local task that creates or saves function examples, list each resulting file in project-root `_partials/` or `_boosterAI/_partials/` as a clickable link when the current host supports a valid file-link format. Verify that each target exists and use the actual path, not a guessed URL or an unrelated file. Include a short purpose and the observed test status. If valid clickable local links are unsupported, give the exact absolute path in the authorized local audience and state that limitation; do not claim a link was delivered or opened. Keep private local paths in the authorized local task audience, not public repository reports or another project. These are navigation links for reading examples, never production dependencies.

## Optional per-step backup

Only if the user requests it and identifies/authorizes the destination and scope, back up each verified step to GitHub using the host's supported existing path. Review the diff for secrets and unrelated data; do not publish private code to a public destination without authorization. Record verified remote branch/commit readback, not just local commit or command exit. If unavailable/rejected, record BACKUP_FAILED with the actual reason and preserve local work. Continue independent authorized work unless the user's instructions make successful backup a prerequisite. No GitHub SDK, remote account or network is required for the core workflow, and the scaffold never performs a push automatically.

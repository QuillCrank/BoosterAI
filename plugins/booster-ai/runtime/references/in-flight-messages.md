# In-flight message routing

Load this workflow when a correction, STOP, related addition or independent request arrives during active work. Use the [host integration and evidence](host-adapter.md) workflow to select a supported interface and check receipt, action and completion separately.

This is requirement 43's host-executed workflow, not an autonomous listener, scheduler or agent launcher. Keep the existing task owner and project record. Never assume a message reached an active task merely because another tool accepted it.

1. **Receive and deduplicate.** Use the host's supported message delivery/readback. Record the source message identity in the existing project record, with the affected task and last processed identity. Reconcile an uncertain send before retrying; do not dispatch the same request twice. Do not copy private message content into the shared skill or public archive.
2. **Classify before dispatch.** Separate a correction or STOP from related additions, independent new work, and blocking ambiguity. STOP or cancellation takes precedence for affected work; changed requirements invalidate affected acceptance evidence. Do not keep executing a contradicted requirement just to avoid interruption. Clarify only genuinely blocking ambiguity, following requirement 40.
3. **Related additions.** When useful and supported, assign a separate subagent a bounded review of the new details. Give it the relevant context, acceptance criteria and non-overlapping ownership; use read-only review when the main owner is editing the same files. The main owner incorporates the result at the next safe dependency boundary and revalidates affected work. Continue unaffected critical-path work meanwhile.
4. **Independent work.** Delegate each ready independent job to an appropriate autonomous subagent when authority, capacity and supported tools permit. Give explicit inputs, outputs, dependencies, allowed files, acceptance tests and handoff. Preserve existing claims; never overlap conflicting writes or shared-target actions. Dependent jobs wait for verified prerequisites, not an agent's completion claim.
5. **Unsupported or full host.** If live message delivery, subagent spawning or capacity is unavailable, keep the request pending in the existing project record and process it serially at a safe checkpoint. Report a material limitation; do not install a background worker, interrupt an active turn to fake delivery, invent agent IDs or claim automatic parallel execution.
6. **Integrate and close.** Distinguish received, dispatched, started, delivered and verified. Retain returned agent/run identifiers and observable start/end evidence when available; overlapping times demonstrate only those runs' concurrency. Review each result, run the relevant real-target acceptance tests against the resulting revision, and update only affected records. A delivered result is not verified integration. Keep the final report short and explicit about remaining blockers.

Existing authorization, mandatory approvals, access-denial handling, STOP, project privacy and single-owner rules remain in force. This routing does not expand permission or change host configuration. No universal guarantee of uninterrupted execution, automatic delivery or maximum parallelism is made.

# User delivery and evidence

Load this workflow before running a necessary, permitted PowerShell command.
Also load it for progress updates, user corrections, and result or file
delivery. Use the user's language. Briefly report a material change, what was actually checked, and the
next action or concrete blocker if one remains.
Start with the development itself and give the reader only useful context.
Skip formulaic agreement or apologies at the start. Keep the closing
focused on the work and omit self-focused apologies and complaints.
Keep feedback candid and free of flattery.
Supply the requested detail or the context needed to act. If a proposal is
incorrect or risky, address the idea, explain the reason, and give a viable
alternative when one exists. When the user corrects a decision or scope, apply
the correction. Record material issues and the practical lesson and effect of
an explicit correction in the existing project record.

## Report the observed state

Keep planned, implemented, tested and verified in the actual target separate.
Name the exact scope of each result. Use PASS when the scoped criterion has
actual acceptance evidence, FAIL for an observed criterion failure, and
NOT VERIFIED when the evidence is insufficient. Use NOT_RUN for a specific
check that did not run, and give its concrete missing prerequisite. Describe
controlled checks with their own scope.

For source publication and installed use, follow the
[source and package publication procedure](publication-privacy.md#source-and-package-publication)
and report the evidence for each.

## Deliver files and observe the result

For each requested file, verify that the exact target exists inside the
authorized project. Give its purpose and observed test status. Apply these
checks to delivered examples from either supported partials location. Use
the host's supported local link format and the exact verified target. If the
host cannot provide an openable link, give the full absolute path and state
the limitation in the authorized local audience. Keep private paths out of
public output.

For a Codex file panel request, use the calling task by default. Specify
another task only at the user's request.

Treat file existence, link delivery and visible opening as distinct
observations. Check the supported host view when acceptance requires visible
behavior and access is available. A queued panel request establishes submission.
Record an unobserved rendering or opening as NOT_RUN.

## PowerShell execution and recovery

If a user-requested task needs a permitted PowerShell command, its
authorized owner runs that command first. Diagnose a genuine failure and
reconcile uncertain effects before using a materially different permitted
approach. If that second attempt also fails, give a one-sentence reason and
the exact permitted command using the applicable host output instructions.
Route an access refusal or STOP through the existing recovery and
authorization rules.

For a live acceptance exercise, use a genuine user-requested operation and
record the observed command outcomes and applicable host behavior.
